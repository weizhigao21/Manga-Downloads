> 撰写日期：2026-09-30
> 目标版本：v1.3.0
> 状态：**已实现**（阶段 1-4 全部完成，233 项测试通过）
>
> 实现说明：按第七节分阶段落地，核心链路（本地优先 / 边看边下边缓存 / 压缩包作品可读 /
> 缓存与下载目录合流）均已打通并有测试守卫。实现中发现并修复了一个关键稳定性缺陷：
> 无事件循环场景下关闭阅读器会因 QThread 未等待而 abort（exit code 127），已在
> `ReaderWindow._shutdown_workers` 中以「请求中断 + 限时 join + 超时 terminate」解决，
> 并配了可在缺失 wait 时精准失败的回归用例。

## 一、结论先行

**可行，且与现有架构契合度很高。**

理由三条：

1. **数据链路已存在。** 「边看边下」所需的全部能力（阅读页 URL 提取、逐页图片直链解析、并发下载、断点续传跳过、原子写盘）在 `src/downloader.py` + `src/wnacg_crawler.py` 里已经实现并被测试覆盖，阅读器只需**按页复用**这些函数，不必新写网络层。
2. **本地图片的落盘位置是可预测的。** 图片模式下载后是 `[分类标签] 显示名/页码.jpg`，压缩包模式解压后同样是这个目录。只要复用 `_download_folder_name()` / `_match_download_folder()` 的命名规则，阅读器就能**通过目录反查**到本地图片，无需额外索引。
3. **界面层是分层干净的。** `ui/` 只依赖 `src/`，新增一个 `ui/reader/` 模块 + 卡片上一个「阅读」按钮即可，不动核心逻辑，回归风险可控。

**唯一的实质性风险**是站点反爬压力：在线阅读时每翻一页都要解析图片列表页（每张图还要解析一次详情页），请求密度远高于「整部下载」。必须把节流/预取做成可配置，否则容易被限流。方案里已给出应对（见第四节 F3）。

## 二、现状盘点（方案的事实基础）

### 2.1 已有的可复用能力

| 能力 | 位置 | 阅读器怎么用 |
| --- | --- | --- |
| 详情页 → 阅读页 URL（含总页数） | `src/downloader.py::_extract_reading_page_url` | 打开阅读器时取总页数与阅读页基准 URL |
| 阅读页 → 每页图片直链（分批） | `src/wnacg_crawler.py::parse_picture_page(reading_url, start, end)` | 预取窗口：只解析「当前页 ± N」的直链 |
| 并发下载 + 断点续传跳过 + 原子写 | `src/wnacg_crawler.py::download_pictures(pictures, save_dir, ...)` | 图片缓存到本地，已存在非空则跳过（天然复用缓存） |
| 下载目录命名规则 | `src/downloader.py::_download_folder_name` | 阅读器缓存目录与下载目录**同名**，两者互认 |
| 反查本地已有目录 | `ui/database.py::_match_download_folder` | 判断「这部作品本地有没有，在哪个目录」 |
| 已下载判定 | `ui/database.py::is_downloaded / is_comics_downloaded` | 卡片角标、阅读按钮状态 |
| 全局节流 + 退避重试 | `src/net.py::_throttle / fetch_with_retry` | 阅读时解析请求共用同一节流，不会绕过反爬控制 |

### 2.2 关键事实：下载产物的目录长这样

图片模式（`Download_mode=image`）：

```
Download/
└── [單行本／漢化] 作品显示名/
    ├── 1.jpg
    ├── 2.jpg
    ├── 3.jpg
    ├── ...
    └── title_info.json      # {"original_title":..., "translated_title":...}
```

压缩包模式（`Download_mode=zip`）解压后**目录结构完全一致**（同样是逐张 jpg + `title_info.json`），区别只是「先整包下载再解压」。

> 这直接回答了你的问题：「别的作品是通过压缩包下载的，也可以直接从这个按钮进行阅读」——**可以**，因为压缩包解压完的落盘形态和图片下载一模一样，阅读器不需要区分来源。

### 2.3 目录命名的两个坑（阅读器必须处理）

1. **同翻译名不同作品**会追加 ` (aid)`，如 `[單行本] 作品名 (123456)`。
2. **图片文件名不可控**：`download_pictures` 用的是阅读页里 `<span class="name">` 的文本清洗后 + `.jpg`（`src/wnacg_crawler.py:462`）。实测通常是 `1.jpg`、`2.jpg`，但理论上也可能是别的名字。

→ 所以**不要靠文件名排序**，要**按自然排序（natural sort）扫目录下的图片文件**。这一点在方案里作为硬约束写进实现要求。

## 三、功能形态确认（我按你的描述归纳）

你要的是：

1. **阅读界面**：一个能整屏看图的窗口，上一页/下一页，键盘翻页。
2. **边看边下边缓存**：看第 N 页时，后台把第 N+1、N+2… 页也拉下来存到本地。
3. **重复观看优先走本地**：再看同一部时，先查本地有没有图，有就直接读盘，不联网。
4. **压缩包下载的作品也能读**：同上，走同一个本地目录。
5. **格式统一**：在线看的缓存结果，要和「下载」得到的产物是同一种格式（目录 + jpg），这样两边可以合流。

我理解到位了。下面是方案。

- **连续滚动**：垂直拼接，接近网页阅读体验；实现上仍复用同一套图片加载，只是布局从「单页」变「多页纵向」。

### F2. 图片解析与缓存策略（核心）

这是整个功能的心脏。设计成三层：

```
┌── 展示层 ────────────────────────────────────────┐
│  ReaderWindow 请求第 N 页                          │
└───────────────┬──────────────────────────────────┘
                │  get_page(N)
┌───────────────▼──────────────────────────────────┐
│  PageProvider（ui/reader/page_provider.py）       │
│  ① 本地缓存命中？ ──是──▶ 直接返回本地文件路径        │
│  ② 否：查直链缓存 → 下载 → 写盘 → 返回路径           │
│  ③ 后台触发预取窗口 [N+1, N+PREFETCH]              │
└───────────────┬──────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────┐
│  core 层（复用现有 src/ 函数，不改协议）             │
│  parse_picture_page() / download_pictures()       │
└──────────────────────────────────────────────────┘
```

**关键设计点：**

**(a) 本地优先，不联网**
打开作品时先做一次「本地图片扫描」：
- 用 `_match_download_folder` 的规则定位本地目录；
- 扫目录下所有图片后缀文件，自然排序，得到 `list[Path]`；
- 若列表非空 → **这部作品直接进入「离线可读」状态**，翻页零网络请求。

**(b) 直链索引持久化（可选但强烈建议）**
图片直链一旦解析出来就记进 SQLite，下次重看不必再解析（每页 1 次请求，很值钱）。新表：

```sql
CREATE TABLE IF NOT EXISTS reader_pages (
    aid          TEXT NOT NULL,
    page_no      INTEGER NOT NULL,
    image_url    TEXT NOT NULL,
    local_name   TEXT,            -- 本地缓存文件名（如 "1.jpg"）
    fetched_at   TEXT,
    PRIMARY KEY (aid, page_no)
);
```

直链一般带时效签名，需要在读取时判断是否过期（简单做法：记录 `fetched_at`，超过 N 小时丢弃重取）。

**(c) 预取窗口**
- `PREFETCH_AHEAD`（默认 3）：向后预取 3 页；
- `PREFETCH_BEHIND`（默认 1）：向前预取 1 页（用户常来回翻）；
- 预取在**独立低优先级线程**里跑，复用 `download_pictures` 的 `max_workers`；
- 预取任务**可取消**：用户快速翻页时，丢弃已滑出窗口的任务，避免请求堆积。

**(d) 与「下载任务」共存**
阅读器缓存和完整下载**写同一个目录**。这带来两个好处：
- 看了 20 页之后再点「下载」，前 20 页因断点续传**直接跳过**；
- 用户看到的「已下载」判定天然一致。

> 副作用：读了一半的作品目录里只有部分图片。`is_downloaded` 会判为「已下载」吗？**会**（它只看目录是否存在）。这点需要决策，见第六节 Q2。

### F3. 反爬压力控制（重点风险）

在线阅读的请求量估算：

| 阶段 | 请求数 |
| --- | --- |
| 打开作品（详情页 + 阅读页） | 2 |
| 解析 1 页图片直链 | 1 次列表页 + K 次图片详情页（K = 该页图片数） |
| 下载 1 张图 | 1 |

一部 18 页作品全看完 ≈ **2 + 18×(1+K) + 总图数**，若 K=20、总图 360，约 **700+ 请求**。现有节流是 `0.6s/请求`（`src/net.py:19`），全解析完要 **7 分钟**，明显太慢——但**不能因此放开节流**。

**建议策略：**
1. **按需解析，不预解析全本。** 只解析「当前页 ± 预取窗口」，用户没翻到就不解析。这样实际请求量与阅读速度线性相关，而不是一次性爆炸。
2. **预取窗口默认保守**（前 1 后 3），提供设置项 `reader_prefetch_pages`（范围 0-10）。
3. **缓存的直链复用**：重看时零解析请求。
4. **共享全局节流**：阅读器的所有请求都走 `src/net.py::_throttle`，不新开通道。
5. **失败降级**：某页解析失败时，界面显示「本页加载失败，点击重试」，不阻塞翻页。

> 若实测仍被限流，可加开关 `reader_prefetch_enabled = false`，退化为「纯按需、零预取」模式，请求量与手动逐页下载相当。

### F4. 入口与界面接入点

**(1) 卡片按钮（主入口）**

`ui/widgets/comic_card.py` 右下角按钮区新增「阅读」按钮，放在「下载」左侧。**阅读按钮左侧带一个环形进度圈**，显示本地缓存进度：

```
┌──────────────────────────────┐
│  (◐) [ 阅读 ]  [ 下载 ]       │   ← 圆圈 20px 在按钮左侧，二者按行排列
└──────────────────────────────┘
```

**环形进度圈设计（用户指定要求）：**

用 `QPainter` 画一个圆环，圆环**底色是一圈浅灰**，上面**覆盖一圈彩色弧**，弧的长度等于缓存百分比：

| 缓存进度 | 圆环表现 | 文字 |
| --- | --- | --- |
| 0%（无本地文件） | 整圈浅灰，无彩色弧；或直接隐藏圆环 | 无 |
| 50% | 一半彩色弧（如从 12 点顺时针到 6 点）+ 一半灰底 | `50%` 或 `50` |
| 100% | 整圈彩色（绿） | 对勾 ✓ 或 `100` |

- 圆环尺寸 ~20px，线宽 ~3px，中间写百分比数字（0-99 时显示数字，100 时显示 ✓）；
- 弧从 12 点方向顺时针增长，视觉效果就是"颜色只显示一半正好 50%"；
- 颜色可配置：进行中橙色 `#F97316`，完好绿色 `#16A34A`；底色浅灰 `#E5E7EB`；
- 鼠标悬停 tooltip 显示 `已缓存 120 / 240 张（50%）`。

> 暂不做「下载中也跟着转圈」的动态效果（用户提到"如果有添加的话，圆圈也跟着添加就好了"）——v1.3.0 先做**静态缓存进度圈**；若阅读器正在后台补拉，圆环可通过定时刷新呈现增长，这已足够表达"跟着添加"。

姿态随状态变化：

| 本地状态 | 进度圈 | 阅读按钮 | 下载按钮 |
| --- | --- | --- | --- |
| 无本地文件 | 隐藏（0%） | 「阅读」（在线读，边看边缓存） | 「下载」 |
| 部分缓存 | 橙色半环 + `50%` | 「阅读」（本地优先，缺的补拉） | 「下载」 |
| 完整本地文件 | 绿色满环 + `✓` | 「阅读」（纯本地，不联网） | 「已下载」 |

**(2) 右键菜单**

现有右键菜单加一项：

```
复制作品名称
─────────────
阅读作品            ← 新增（灰色圆点）
查看类似作品
─────────────
翻译作品名称
```

**(3) 下载管理对话框**

已在下载中的任务，双击行可直接进入阅读器（边下边看）。

**(4) 本地作品直接阅读（你说的"压缩包下载的也能读"）**

两个入口：
- 卡片按钮：压缩包下载完的作品，卡片显示「已下载」，点「阅读」直接走本地目录；
- **新增「本地作品库」入口**（可选，v1.3.1）：主窗口工具栏加一个「本地」按钮，扫描 `Download/` 下所有含图片的目录，列成网格，纯离线浏览。这样「用压缩包下载的一堆作品」有了统一入口。

## 七、分阶段实施建议

**阶段 1：骨架与本地优先（可独立验证）**
- `cache_index.py`：本地目录扫描 + 自然排序 + 直链索引表；
- `reader_window.py`：窗口 + 单页显示 + 上下翻页 + 快捷键；
- 此时**只读本地**，无网络。可写完整测试（给定目录 → 能翻页）。

**阶段 2：在线补拉与预取**
- `page_provider.py`：本地未命中 → 解析直链 → 下载 → 展示；
- `prefetch_worker.py`：预取窗口，可取消；
- 打通「边看边下边缓存」。

**阶段 3：接入界面**
- 卡片「阅读」按钮、右键菜单、主窗口连接；
- 下载管理对话框双击进入阅读；
- 设置项 + 样式。

**阶段 4：打磨**

## 八、验收标准（用来判定功能真的做完了）

1. 打开一部**从未下载**的作品，能逐页阅读，且缓存目录逐步长出 jpg 文件；
2. 关闭后重新打开同一部，**断网**仍能读到已缓存的部分（本地优先生效）；
3. 打开一部**用压缩包模式下载**的作品，直接可读且不联网；
4. 从阅读器退出后再点「下载」，已缓存部分**不重复下载**（断点续传生效）；
5. 快速连续翻页 20 次，不崩、不卡死、不出现 "QThread: Destroyed while thread is still running"；
6. 全部测试离线通过，`ruff check src ui tests run_ui.py` 无告警。

## 九、风险与对策汇总

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 站点反爬限流 | 阅读卡顿/失败 | 按需解析 + 保守预取 + 共享节流 + 可关闭预取（F3） |
| 图片文件名不规范 | 排序错乱 | 强制自然排序，不依赖文件名语义 |
| 直链签名过期 | 重看时 404 | 索引记 `fetched_at`，超期失效重取 |
| 阅读线程未收尾 | 退出闪退 | 复用项目既有约定：业务信号命名 `done`，清理挂原生 `finished` |
| 阅读缓存污染「已下载」 | 角标误报 | Q2 的图片数比对方案 |
| 内存占用（大图） | 卡顿 | 只保留前后各 2 页 QPixmap，其余释放；原图按需从磁盘重载 |

## 十、一句话总结

现有的下载器已经把「解析直链 → 并发下载 → 断点续传 → 落盘成标准目录」这条链路做完了，阅读器本质上是**给这条链路套一个按页驱动的 UI + 一个本地优先的缓存查询**。压缩包下载的作品因为解压后目录同构，天然可读。工作量集中在 UI 与缓存编排，核心层几乎不动，可行且风险可控。
